<a id="how-to-read-a-report"></a>

## วิธีอ่านรายงาน

แต่ละแถวของรายงานแสดง metric ID หนึ่งตัว พร้อมหน่วย ค่า จำนวนรอบ และ CV

| คอลัมน์หรือเครื่องหมาย | ความหมาย |
|---|---|
| Value | **ค่ากลาง (median)** ของทุกรอบ ค่ากลางไม่ถูกดึงด้วยรอบที่ช้าหรือเร็วผิดปกติเพียงรอบเดียว |
| Rounds | จำนวนครั้งที่รันการทดสอบนั้น ถ้ามีรอบเดียว จะไม่รู้ว่าผลแกว่งระหว่างรอบแค่ไหน |
| CV | สัมประสิทธิ์การแปรผัน คือส่วนเบี่ยงเบนมาตรฐานคิดเป็นเปอร์เซ็นต์ของค่าเฉลี่ย CV น้อยแปลว่าเครื่องให้ผลเหมือนเดิมทุกครั้ง |
| `*` | วัดครั้งเดียว ให้ถือเป็นข้อบ่งชี้ ไม่ใช่ข้อเท็จจริง |
| `!` | CV ตั้งแต่ 5% ขึ้นไป เครื่องไม่นิ่งระหว่างการทดสอบนี้ (VM อื่นแย่งทรัพยากร, ถูกลดความเร็ว, มีงานเบื้องหลัง) ให้หาสาเหตุก่อนนำไปเปรียบเทียบ |

ในการเปรียบเทียบ (`vmbench report compare A B`) โฟลเดอร์แรกเป็นฐาน และโฟลเดอร์อื่นทั้งหมดถูกตัดสินเทียบกับฐานนั้น:

- **better / worse (ดีกว่า / แย่กว่า)**: ความต่างมากกว่าความแกว่งของทั้งสองการรัน
- **not clearly different (ไม่ต่างกันชัดเจน)**: ความต่างอยู่ภายใน CV ที่มากกว่าของสองการรัน หรือภายใน 1% อย่ารายงานว่าฝั่งใดชนะ
- ค่าบริบท (ทิศทาง `none` เช่น CPU steal) แสดงให้เห็นแต่ไม่ถูกตัดสิน

อ่านคำเตือนที่ด้านบนของรายงานก่อนเสมอ เวอร์ชัน vmbench หรือ cpubench ที่ต่างกัน, `QUICK=1`, ขนาดการทดสอบหรือจำนวน vCPU ที่ต่างกัน, CPU steal สูง และ step ที่ล้ม แต่ละข้อทำให้การเปรียบเทียบไร้ความหมายได้

<a id="excel-review-sheet"></a>

## ชีท Excel สำหรับ review

`vmbench report xlsx DIR [DIR...]` เขียนตัวเลขชุดเดียวกับ `report.md` ลงไฟล์ Excel สำหรับประชุม review (`DIR1/review.xlsx` ถ้าไม่ระบุ `-o`; โฟลเดอร์แรกคือ baseline) ต้องมี openpyxl ซึ่ง `report show` และ `report compare` ไม่ต้องใช้: `sudo apt-get install python3-openpyxl`

แถวมาจาก catalog ของ metric (`vmbench run --metrics`) ทุก ID จึงมีแถวเสมอไม่ว่าจะวัดหรือไม่ และค่าที่ว่างจะบอกเหตุผลในคอลัมน์ Note เสมอ: `stage not run`, step ที่ล้ม (`disk / fio randread8k = FAIL exit 1, ...`) หรือ `no value`

| ชีท | มีอะไร |
|---|---|
| Review | `Section, Details, Tooling, Owner, Priority, Unit, Better` แล้วต่อรัน `<label>` (ค่ามัธยฐาน), `CV <label>`, `Rounds <label>` (จำนวนค่าที่รันนั้นมีจริง); ถ้ามีสองรันขึ้นไป `Diff % <label> vs <baseline>` (เป็นค่า ไม่ใช่สูตร) และ `Verdict <label>` (ผลเดียวกับ `report compare`); ตามด้วยค่าแต่ละรอบ `<label> r1, r2, ...`; `Note`; `ID` แถวสีเทา: วัดรอบเดียว CV สีส้ม: 5% ขึ้นไป |
| Hardware | ทุกฟิลด์ของ `hardware.json` คอลัมน์ละรัน และ `Same?`; DIMM, NIC, ดิสก์ แถวละตัว รันที่ไม่มี `hardware.json` (vmbench v0.1.0 หรือเก่ากว่า) คอลัมน์ว่างพร้อมหมายเหตุ ถ้ามี `hardware.txt` แต่ละหัวข้อจะอยู่ในเซลล์เดียว |
| Summary | ตารางสภาพแวดล้อมและคำเตือนของ `report.md` และวิธีอ่านสีและผล |
| CPU 1t vs max | ค่า 1 thread และทุก vCPU ของการทดสอบ CPU แต่ละตัว และอัตราส่วน |
| Raw `<label>` | `results.tsv` ของแต่ละรันตามจริง |

**layout.tsv** จัดชีท Review ให้เรียงแบบ checklist ของทีม เป็นไฟล์ของทีม เก็บไว้นอก repo และส่งด้วย `--layout FILE`; `vmbench report layout > layout.tsv` พิมพ์ไฟล์ตั้งต้นที่มีทุก ID เป็น UTF-8 คั่นด้วย tab บรรทัดแรกเป็น header และ `#` คือ comment:

```
section	id	name	owner	priority	note
CPU	hw:cpu.stepping	CPU stepping	Vendor	Must have
	cpu.sysbench.prime.1t	sysbench 1 thread	Team A	Must have	ไม่ใช้ตัดสิน x86 vs ARM (ขึ้นกับ compiler)
Application		Node JS transactions	Team D	Nice to have
```

- `section`: มีแถวหัวข้อทุกครั้งที่เปลี่ยน ว่าง = หัวข้อเดียวกับแถวบน
- `id`: metric ID (ID ที่ไม่รู้จักเป็น error ที่บอกชื่อ ID และบรรทัด); `hw:<path>` สำหรับฟิลด์ของ `hardware.json` เช่น `hw:system.bios_version`, `hw:memory.populated`, `hw:nics[].firmware` (ค่าเป็นข้อความ ผลคือ `same` / `differs` path ที่ไม่มีในไฟล์ได้เซลล์ว่างกับ `not in hardware.json`); หรือว่างสำหรับแถวที่กรอกเอง
- `name`: ว่าง = ข้อความ "what it measures" ของ catalog; `owner`, `priority`: ข้อความอะไรก็ได้; `note`: ต่อท้ายคอลัมน์ Note
- ID ที่ layout ไม่ได้พูดถึงไม่หาย ไปอยู่หัวข้อสุดท้าย "Other measured values"

`--lang th` (หรือ `VMBENCH_LANG=th`) ให้หัวคอลัมน์และหมายเหตุเป็นภาษาไทย `vmbench report xlsx` ไม่แก้ไฟล์ Excel ที่ไม่ได้สร้างเอง: ไฟล์ `-o` ที่มีอยู่แล้วและไม่ได้สร้างโดย vmbench จะถูกปฏิเสธ

<a id="ideas-that-apply-to-every-stage"></a>

## หลักที่ใช้กับทุก stage

**Throughput กับ latency เป็นคนละคำถาม** throughput (IOPS, MB/s, TPS, RPS, Gbps) คือปริมาณงานที่เครื่องทำเสร็จต่อวินาทีเมื่อมีงานป้อนตลอด latency (us, ms, ns) คือเวลาที่งานชิ้นเดียวใช้ เครื่องหนึ่งอาจมี throughput สูงแต่ latency แย่ได้ในเวลาเดียวกัน และผู้ใช้มักรู้สึกจาก latency

**เปอร์เซ็นไทล์บอกเรื่องคำขอที่ช้า** p99 คือค่าที่ 99% ของการทำงานเร็วกว่า p99.9 คือค่าที่ 99.9% เร็วกว่า ถ้าหน้าเว็บหนึ่งหน้าต้องอ่านดิสก์ 50 ครั้ง การอ่านที่ช้า 1 ใน 100 ครั้งจะกระทบสัดส่วนใหญ่ของการเปิดหน้าเว็บ p99 และ p99.9 จึงมักสำคัญกว่าค่าเฉลี่ย

**`1t` กับ `max` ตอบคนละคำถาม** `1t` (หนึ่ง thread) บอกว่างานเดี่ยวทำได้เร็วแค่ไหน ซึ่งเป็นตัวจำกัดเวลาตอบสนองของงานที่แบ่งย่อยไม่ได้ เช่น query ฐานข้อมูลหนึ่งตัวหรือคำขอหนึ่งรายการ `max` (ทุก vCPU) บอกความสามารถรวมเมื่อมีงานหลายชิ้นพร้อมกัน อัตราส่วน `max / 1t` บอกว่าเครื่องกระจายงานไปยัง vCPU ได้ดีแค่ไหน ถ้าต่ำกว่าจำนวน vCPU มาก อาจเป็นเพราะใช้ core จริงร่วมกัน, ถูกจำกัดด้วยความร้อนหรือพลังงาน หรือแบนด์วิดท์หน่วยความจำไม่พอ

**มากดีกว่า ยกเว้นหน่วยที่เป็นเวลาหรือจำนวนเหตุการณ์ที่ไม่ดี** `ns`, `us`, `ms`, `count` และ packet loss น้อยดีกว่า ส่วนอื่นทั้งหมดมากดีกว่า รายงานใช้กฎนี้ให้แล้ว

**VM สะท้อน hypervisor พอ ๆ กับฮาร์ดแวร์** ผล disk รวม cache และการตั้งค่า storage ของ host ผล CPU ขึ้นกับรุ่น CPU ที่ hypervisor เปิดให้ guest เห็น และ VM อื่นบน host เดียวกันแย่งเวลาไปจาก VM ของคุณ (CPU steal) ความต่างมากระหว่างสอง VM อาจมาจากการตั้งค่า ไม่ใช่จากฮาร์ดแวร์

## cpu

วัดว่า vCPU รันโค้ดประเภทต่าง ๆ ได้เร็วแค่ไหน ความเร็ว CPU มีผลกับเกือบทุกอย่าง: การรับคำขอ, การบีบอัด, การเข้ารหัส, การรัน query, การ build

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `cpu.sysbench.prime.1t`, `cpu.sysbench.prime.max` | มาก | ลูปเลขจำนวนเต็มแบบง่าย ใช้เช็กเร็ว ๆ ระหว่างเครื่อง **สถาปัตยกรรมเดียวกัน** เท่านั้น คะแนนขึ้นกับ compiler และชุดคำสั่ง จึงห้ามใช้เทียบ x86 กับ ARM |
| `cpu.7z.rating.max` | มาก | benchmark ในตัวของ 7-Zip ที่บีบอัดและคลายการบีบอัด แทนงานเลขจำนวนเต็มทั่วไปที่มีการแตกแขนงและเข้าถึงหน่วยความจำ: การบีบอัด, ทำไฟล์ archive, งาน server หลายประเภท |
| `cpu.openssl.aes-256-gcm.1t`, `cpu.openssl.aes-256-gcm.max` | มาก | ความเร็วการเข้ารหัสด้วย AES ของฮาร์ดแวร์ สำคัญกับ TLS (HTTPS), VPN, ดิสก์เข้ารหัส และ backup เข้ารหัส ถ้าค่าต่ำมาก อาจแปลว่า guest มองไม่เห็นคำสั่ง AES ของ CPU (ตรวจชนิด CPU ที่ hypervisor เปิดให้) |

การทดสอบของ cpubench แบ่งงาน CPU เป็นหมวด แต่ละหมวดบันทึกทั้งแบบหนึ่ง thread และทุก vCPU ชื่อแต่ละตัวด้านล่างจึงแทน ID สองตัว เช่น `cpu.cpubench.int.json.1t` และ `cpu.cpubench.int.json.max` หน่วยมาจาก cpubench และต่างกันในแต่ละการทดสอบ แต่ภายในการทดสอบเดียวกัน ค่ามากดีกว่าเสมอ

| การทดสอบของ cpubench | แทนงานจริงแบบใด |
|---|---|
| `cpu.cpubench.int.compress.{1t,max}`, `cpu.cpubench.int.decompress.{1t,max}` | การบีบอัดใน web server (gzip), การจัดการ log, backup, layer ของ container image |
| `cpu.cpubench.int.hashmap.{1t,max}` | การค้นหาในตารางในหน่วยความจำ: cache, interpreter, application server ไวต่อ latency ของ cache และหน่วยความจำ |
| `cpu.cpubench.int.json.{1t,max}` | การแปลง JSON ไปและกลับ: เกือบทุก web API และ microservice |
| `cpu.cpubench.int.regex.{1t,max}` | การจับคู่รูปแบบข้อความ: แยก log, ตรวจข้อมูลนำเข้า, routing, ค้นหา |
| `cpu.cpubench.int.sort.{1t,max}` | การเรียงลำดับ: ฐานข้อมูล (ORDER BY, สร้าง index), ประมวลผลข้อมูล |
| `cpu.cpubench.float.fft.{1t,max}` | ประมวลผลสัญญาณ, งานเสียงและภาพ |
| `cpu.cpubench.float.matmul.{1t,max}` | คณิตศาสตร์เมทริกซ์: งานคำนวณเชิงตัวเลข, รันโมเดล machine learning แบบง่าย ได้ประโยชน์จากคำสั่งแบบ vector |
| `cpu.cpubench.float.nbody.{1t,max}` | การจำลองทางวิทยาศาสตร์ด้วยเลขทศนิยม |
| `cpu.cpubench.crypto.aes-gcm.{1t,max}` | เข้ารหัสข้อมูลปริมาณมาก (ข้อมูลใน TLS, เข้ารหัสดิสก์) |
| `cpu.cpubench.crypto.sha256.{1t,max}` | การทำ hash: checksum, ระบุเนื้อหาด้วย hash, ลายเซ็น, ตัดข้อมูลซ้ำ |
| `cpu.cpubench.crypto.ecdsa-p256.{1t,max}`, `cpu.cpubench.crypto.rsa2048-sign.{1t,max}` | งานกุญแจสาธารณะ: TLS handshake และการเซ็น token สำคัญกับ server ที่รับการเชื่อมต่อ HTTPS ใหม่จำนวนมาก |

วิธีอ่านกลุ่ม cpu:

- ดูหมวดที่ตรงกับงานของคุณ แทนการดูตัวเลขรวมตัวเดียว CPU สองตัวอาจชนะกันคนละหมวด
- บริการที่ต้องตอบเร็ว ให้ดูค่า `1t` เป็นหลัก งาน batch และผู้ใช้จำนวนมากพร้อมกัน ให้ดูค่า `max`
- CV สูงในกลุ่มนี้มักแปลว่ามี VM อื่นใช้ core จริงตัวเดียวกัน ให้ดู CPU steal ของการรันเดียวกัน

## mem

วัดว่า vCPU ย้ายข้อมูลเข้าออก RAM ได้เร็วแค่ไหน และการเข้าถึงหน่วยความจำหนึ่งครั้งใช้เวลาเท่าไร โปรแกรมที่ข้อมูลใหญ่เกิน cache ของ CPU (ฐานข้อมูล, cache, analytics, heap ของแอปขนาดใหญ่) มักถูกจำกัดด้วยหน่วยความจำมากกว่า CPU

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `mem.stream.triad.max` | มาก | แบนด์วิดท์หน่วยความจำเมื่อใช้ทุก vCPU ด้วยรูปแบบอ่าน-อ่าน-เขียน (`a = b + s * c`) เป็นตัวเลขตัวเดียวที่นิยมใช้ตอบว่า "เครื่องนี้ไหลข้อมูลผ่าน RAM ได้กี่ข้อมูลต่อวินาที" สำคัญกับการ scan, analytics, การบีบอัดข้อมูลก้อนใหญ่ และฐานข้อมูลในหน่วยความจำ |
| `mem.stream.copy.max` | มาก | แบนด์วิดท์หน่วยความจำสำหรับการคัดลอกล้วน ใกล้เคียงต้นทุนการย้าย buffer ไปมา (ชั้น network และ storage, การคัดลอกหน่วยความจำก้อนใหญ่) |
| `mem.lmbench.lat-mem-rd.1t` | น้อย | เวลาโหลดหน่วยความจำหนึ่งครั้งเมื่อข้อมูลไม่อยู่ใน cache ของ CPU (ชุดข้อมูลใหญ่ที่สุด, หนึ่ง process) สำคัญกับงานที่ไล่ตาม pointer: hash table, B-tree, โครงสร้างแบบลิงก์, interpreter latency ต่ำทำให้แต่ละขั้นเร็วขึ้น แม้ยังใช้แบนด์วิดท์ไม่เต็ม |
| `mem.stream.triad.cross-numa` | มาก | STREAM triad อีกครั้ง แต่ให้ CPU ของ NUMA node 0 อ่านหน่วยความจำของ node 1 (เฉพาะเครื่องที่มีสองโหนดขึ้นไป) เทียบกับ `mem.stream.triad.max`: ถ้าตกลงมาก คือราคาที่ process จ่ายเมื่อหน่วยความจำไปอยู่อีก socket บอกว่าการวาง NUMA สำคัญแค่ไหนบนเครื่องนี้ สำหรับฐานข้อมูลและ JVM ที่ไม่ได้ pin |

วิธีอ่านกลุ่ม mem:

- แบนด์วิดท์หารด้วยจำนวน vCPU ได้ส่วนแบ่งต่อ vCPU คร่าว ๆ ถ้าต่ำ การเพิ่ม vCPU จะไม่ช่วยให้งานที่หนักด้านหน่วยความจำเร็วขึ้นมากนัก
- latency ที่สูงกว่าเครื่องที่เทียบเคียงได้มาก อาจมาจากหน่วยความจำกระจายข้าม NUMA node หรือ host ขาดหน่วยความจำ
- เทียบแบนด์วิดท์เฉพาะการรันที่มีจำนวน vCPU เท่ากัน เพราะ STREAM ใช้ทุก vCPU

## disk

วัด storage ที่ VM เขียนลง พฤติกรรมของดิสก์กำหนดว่าฐานข้อมูล commit ได้เร็วแค่ไหน แอปเริ่มทำงานเร็วแค่ไหน และ backup กับ restore ใช้เวลานานเท่าไร ใน VM ตัวเลขเหล่านี้รวม cache ของ hypervisor และ storage backend จึงอาจสูงหรือต่ำกว่าดิสก์จริงมาก

การทดสอบแบบสุ่มและแบบเรียงลำดับใช้ direct I/O (ข้าม page cache ของ guest) บนไฟล์ทดสอบขนาด `FIO_SIZE` (ค่าเริ่มต้น 8 GB) หรือบน raw device เมื่อตั้ง `RAW_DEV` ส่วนการทดสอบ WAL ตั้งใจให้ต่างออกไป: เหมือน write-ahead log ของฐานข้อมูล คือเขียนลงไฟล์ใน `WAL_DIR` ตามปกติ แล้วเรียก `fdatasync` เพื่อบังคับให้ข้อมูลลงที่เก็บถาวร

ตำแหน่งของไฟล์ทดสอบถูกบันทึกใน `info.txt` (vmbench 0.2.5 ขึ้นไป) เป็นบรรทัด `fio_where: other  fio_fs: /dev/mapper/datavg-bench  fio_dir: /bench/bench-data` stage info เทียบดิสก์ทั้งลูก (whole disk) ที่อยู่ใต้ filesystem ของ `DATA_DIR` กับของ `/` (`findmnt` แล้วไล่ `lsblk -s` ผ่าน partition, LVM, RAID และ dm-crypt): `os` = ดิสก์ลูกเดียวกับ `/` (โฟลเดอร์บน `/` หรือ LV อื่นใน volume group เดียวกัน), `other` = คนละดิสก์ (LV บนดิสก์ลูกที่สอง), `unknown` = ระบุไม่ได้ (tmpfs, overlay, NFS หรือ filesystem ทางเครือข่ายอื่น, ZFS, container หรือไม่มี/รัน `findmnt`/`lsblk` ไม่สำเร็จ) `fio_fs` คือ device หรือแค่ชนิดของ filesystem เมื่อไม่มี device (source ของ NFS จะมีชื่อเซิร์ฟเวอร์) การตรวจนี้อ่านอย่างเดียวและไม่ทำให้การรันล้ม "คนละดิสก์" หมายถึงคนละดิสก์ในมุมของ guest: virtual disk สองลูกอาจอยู่บน storage เดียวกันของ host ก็ได้ `WAL_DIR` และ `DB_DIR` (การทดสอบ `disk.wal.*` และ `disk.fio.db-*`) ไม่อยู่ในบรรทัดนี้ ดูได้จากส่วน "mounts" ของ `info.txt`

คำเตือนเรื่อง disk ในรายงาน (เฉพาะเมื่อไม่ได้ตั้ง `RAW_DEV`) เป็นไปตามบรรทัดนั้น:

| `fio_where` | คำเตือน |
|---|---|
| `os` | วัดจากไฟล์บน OS disk ตัวเลขอาจรวมผลของ host cache และการตั้งค่า hypervisor ควรตรวจ cache mode |
| `other` | วัดจากไฟล์ใน `fio_dir` บนดิสก์แยก (`fio_fs`) ไม่ใช่ OS disk ตัวเลขยังอาจรวมผลของ host cache และการตั้งค่า hypervisor |
| `unknown` | วัดจากไฟล์ใน `fio_dir` ระบุไม่ได้ว่าอยู่บนดิสก์ไหน ถ้าเป็น `tmpfs` จะบอกว่าค่าเป็นของหน่วยความจำ ไม่ใช่ storage และถ้าเป็น filesystem ทางเครือข่ายหรือที่แชร์จาก host (NFS, CIFS, 9p, virtiofs, ...) จะบอกว่าตัวเลขรวมผลของเครือข่ายและ cache ของเซิร์ฟเวอร์ |
| ไม่มี (vmbench 0.2.4 หรือเก่ากว่า) | วัดจากไฟล์ใน data directory ไม่ได้บันทึกว่าอยู่บนดิสก์ไหน |

## nvme

รันเฉพาะบน bare metal ที่ตั้ง `NVME_DEVS` (ดิสก์เหล่านั้นถูกลบทั้งลูก) ตอบสองคำถามที่การตรวจรับเซิร์ฟเวอร์ถาม: ดิสก์ทั้งชุดให้ได้เท่าไรเมื่อทำงานพร้อมกัน และทุกลูกดีเท่ากันหรือไม่

**ทุกลูกพร้อมกัน** (ยอดรวมที่เครื่องให้ได้; fio หนึ่ง job ต่อดิสก์ในการรันเดียว):

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `nvme.fio.randread-4k.qd32x4.all-disks` | มาก | IOPS อ่านสุ่ม 4 KiB รวมทุกลูก คือเพดานของฐานข้อมูลหรือ object store ที่กระจายข้อมูลลงทุกดิสก์ ถ้าน้อยกว่าผลรวมของค่าต่อลูกมาก แปลว่าดิสก์แย่งคอขวดเดียวกัน (เลน PCIe, switch, ความสามารถ I/O ของ CPU) |
| `nvme.fio.seq-read-1m.all-disks` | มาก | แบนด์วิดท์อ่านเรียงลำดับ (GB/s) รวมทุกลูก คือความเร็ว backup, restore และ scan เมื่ออ่านทุกดิสก์พร้อมกัน |

**ทีละลูก** (`nvme.*.per-disk`; หนึ่งแถวต่อดิสก์ รายงานจึงแสดง **มัธยฐานของทุกลูก** และ CV บอกว่าเหมือนกันแค่ไหน): `nvme.fio.randwrite-4k.qd32x4.per-disk` (เขียนสุ่ม 10 นาที ให้ดิสก์ใหม่พ้นสภาพเร็วช่วงแรก), `nvme.fio.randread-4k.qd1.p99.per-disk` และ `nvme.fio.randread-4k.qd1.p999.per-disk` (หาง latency ของคำขอเดี่ยว), `nvme.fio.randread-4k.qd32x4.per-disk`, `nvme.fio.mixed-70-30-4k.read.per-disk` และ `nvme.fio.mixed-70-30-4k.write.per-disk`, `nvme.fio.seq-read-1m.per-disk`, `nvme.fio.seq-write-1m.per-disk` และ queue-depth sweep `nvme.fio.randread-4k.sweep-qd{1,4,16,32,64,128}.per-disk` ความหมายเหมือนค่า `disk.fio.*` ชื่อเดียวกัน แต่วัดบนดิสก์ดิบ

วิธีอ่านกลุ่ม nvme:

- `!` (CV ตั้งแต่ 5%) บนค่าต่อลูก แปลว่าดิสก์ไม่เหมือนกัน `nvme-per-disk.tsv` บอกว่าลูกไหนช้า ตรวจ firmware (`nvme-devices.txt`), ช่องเสียบ และอุณหภูมิของลูกนั้นก่อนตรวจรับเครื่อง
- เทียบค่าต่อลูกเฉพาะดิสก์รุ่นและ firmware เดียวกัน สองผู้ขายที่ใช้ดิสก์ต่างกันคือกำลังเทียบการเลือกดิสก์ ไม่ใช่เซิร์ฟเวอร์
- ยอดรวมทุกลูกหารด้วยจำนวนดิสก์ เทียบกับมัธยฐานต่อลูก บอกว่าดิสก์ทุกลูกทำงานพร้อมกันได้เต็มที่หรือไม่

## pg

รัน benchmark ของ PostgreSQL เอง (pgbench, งานคล้าย TPC-B ที่เป็นธุรกรรมอ่านเขียนขนาดเล็ก) บน cluster ที่แยกไว้ รวม CPU, หน่วยความจำ และโดยเฉพาะ latency ของการ commit เข้าเป็นตัวเลขที่ใกล้เคียงแอป OLTP จริง

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `pg.pgbench.tpcb.tps` | มาก | ธุรกรรมต่อวินาทีเมื่อมี client 2 × vCPU คือความสามารถของเครื่องในฐานะ database server สำหรับงานที่เขียนหนัก |
| `pg.pgbench.tpcb.stability` | มาก | TPS นิ่งแค่ไหนตลอด 10 นาที 100 คือแบนราบสมบูรณ์ ค่าต่ำแปลว่ามีช่วงสะดุดเป็นระยะ มักมาจาก checkpoint หรือ storage หยุดชะงัก ซึ่งผู้ใช้รู้สึกเป็นช่วงที่ช้า |
| `pg.pgbench.latency.single` | น้อย | เวลาเฉลี่ยต่อธุรกรรมเมื่อมี client เดียว บอกต้นทุนของธุรกรรมหนึ่งรายการเมื่อทำลำพัง ส่วนใหญ่คือความเร็ว CPU บวก latency ของการ commit สำคัญกับแอปที่ทำงานกับฐานข้อมูลทีละขั้น |
| `pg.pgbench.tpcb.tps-per-watt` | มาก | TPS ของ TPC-B หารด้วยกำลังไฟของทั้งเครื่องที่ BMC รายงานระหว่างการรันนั้น (เฉพาะเมื่อมี `ipmitool` แบบ root บน bare metal) คือประสิทธิภาพต่อวัตต์ ตัวเลขเบื้องหลังบรรทัดค่าไฟในการเทียบต้นทุน เทียบเฉพาะการรันที่ `PG_SCALE` และการตั้งค่าเท่ากัน และจำไว้ว่าค่าจาก BMC คือทั้งเซิร์ฟเวอร์ ไม่ใช่ CPU อย่างเดียว |

วิธีอ่านกลุ่ม pg:

- TPS ถูกจำกัดด้วยทรัพยากรที่หมดก่อน มักเป็น latency ของการ commit (เทียบกับค่า WAL ในกลุ่ม disk) บางครั้งเป็น CPU
- ความนิ่งสำคัญพอ ๆ กับ TPS เครื่องที่ TPS ต่ำกว่าเล็กน้อยแต่นิ่งกว่า ให้บริการที่คาดเดาได้มากกว่า
- ผลขึ้นกับขนาดข้อมูล (`PG_SCALE`) และการตั้งค่า PostgreSQL เทียบเฉพาะการรันที่ scale และการตั้งค่าเหมือนกัน (`pg-settings.txt` ในโฟลเดอร์ผลบันทึกค่าเหล่านี้ รวมถึงเวอร์ชันและ data checksums จึงนำสองไฟล์มา diff กันได้)
- บรรทัดแรกของการตั้งค่าคือ profile ที่ใช้ตอน setup (`vmbench.profile` แสดงเป็น *profile ของ PostgreSQL* ในตารางสภาพแวดล้อมด้วย) `bench` ใช้กติกาเบนช์มาร์กเดียวกันทุกเครื่อง ส่วน `production` tune แต่ละเครื่องตาม RAM และ CPU ของตัวเองตามสูตรของ PGTune การเทียบสองการรันที่เป็น `production` จึงเป็นการเทียบเซิร์ฟเวอร์ที่ tune แล้วทั้งคู่ `report compare` จะเตือนเมื่อ profile ต่างกัน ค่า `unset` คือ cluster ที่ตั้งก่อน vmbench 0.2.1 (ใช้กติกา `bench` เว้นแต่มีคนแก้เอง)
- ถ้าค่า stability ต่ำและ `pg-checkpoints.txt` นับ checkpoint ได้ แปลว่าช่วงวัดมี checkpoint แทรก ให้ดูค่า `disk.wal.*` และ `disk.fio.db-*` ประกอบ เพราะ checkpoint คือจุดที่ storage แสดงตัว

## net

วัดเส้นทางเครือข่ายระหว่าง VM นี้กับเครื่องปลายทาง สำคัญกับทุกอย่างที่คุยกับเครื่องอื่น: ฐานข้อมูลที่อยู่อีกเครื่อง, replication, storage ผ่านเครือข่าย, client

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `net.iperf3.tcp.tx`, `net.iperf3.tcp.rx` | มาก | throughput ของ TCP แต่ละทิศทางด้วย 8 stream การทดสอบส่งทั้งสองทาง **พร้อมกัน** สองค่านี้จึงแบ่งลิงก์กัน ไม่มีค่าไหนเป็นเพดานของทิศทางเดียว |
| `net.iperf3.tcp.bidir` | มาก | สองทิศทางรวมกัน เป็นค่าที่ใกล้ความสามารถรวมของเส้นทางที่สุดในสามค่านี้ สำคัญกับ backup, replication และการโอนข้อมูลก้อนใหญ่ |
| `net.sockperf.pingpong.avg` | น้อย | latency เฉลี่ยทางเดียวของข้อความขนาดเล็ก ทุกคำขอไปยังฐานข้อมูลหรือบริการบนเครื่องอื่นต้องจ่ายค่านี้อย่างน้อยสองครั้ง (ไปและกลับ) |
| `net.sockperf.pingpong.p99` | น้อย | ข้อความที่ช้า แสดงออกมาเป็นคำขอระหว่างบริการที่ช้าเป็นครั้งคราว |
| `net.iperf3.udp.pps` | มาก | จำนวน packet UDP ขนาดเล็ก (64 ไบต์) ที่ **ส่ง** ได้ต่อวินาที โดยส่งเร็วที่สุดเท่าที่ทำได้ บอกว่า network stack ของ VM ดัน packet เล็กได้กี่ packet: เกี่ยวกับ DNS, VoIP, เกม และ traffic อื่นที่ถูกจำกัดด้วยอัตรา packet |
| `net.iperf3.udp.loss` | น้อย | packet loss ที่อัตราการส่งแบบไม่จำกัดนั้น เนื่องจากไม่ได้จำกัดความเร็วฝั่งส่ง จึงคาดว่าจะมี loss บ้าง และไม่ได้แปลว่าเครือข่ายเสีย ใช้เทียบเครื่องที่ทดสอบแบบเดียวกัน |

วิธีอ่านกลุ่ม net:

- ผลบรรยาย **เส้นทาง** ไปยังเครื่องปลายทางที่เลือก รวมถึงตัวเครื่องปลายทางเอง เทียบเครื่องกับเครื่องเฉพาะเมื่อใช้ปลายทางเดียวกัน
- สำหรับแอปที่คุยถี่ (คำขอเล็ก ๆ จำนวนมาก) latency สำคัญกว่า throughput

## web

รัน HTTP server ขนาดเล็กและตัวยิงโหลดจาก cpubench บนเครื่องเดียวกัน (loopback) แล้วเพิ่มอัตราคำขอทีละขั้นจน latency ไม่ผ่านเป้าหมายของ cpubench

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `web.cpubench.mix.max-rps` | มาก | อัตราคำขอสูงสุดที่เครื่องรับได้ก่อน latency เริ่มพุ่งขึ้นชัน ("จุดหักเข่า" หรือ knee) เป็นตัววัดในทางปฏิบัติว่า CPU รับ traffic เว็บหรือ API ได้เท่าไรโดยยังตอบสนองดี |

server ได้ vCPU ครึ่งหนึ่ง ตัวยิงโหลดได้อีกครึ่ง (2 vCPU: 0 | 1, 8: 0-3 | 4-7, 16: 0-7 | 8-15 ดูได้จาก log และ `web_cpus` ใน `meta.json`) ค่าจึงโตตามขนาดเครื่องและแทนครึ่งเครื่อง ผลจาก vmbench 0.2.2 หรือเก่ากว่าใช้ 0-3 | 4-7 เสมอ จึงล้มบนเครื่องที่มีน้อยกว่า 5 vCPU และใช้แค่ 8 CPU บนเครื่องที่ใหญ่กว่า อย่าเทียบค่า web ของผลเก่ากับผลใหม่ เว้นแต่เครื่องมี 8 vCPU พอดี

วิธีอ่านกลุ่ม web:

- ทั้ง server และตัวยิงโหลดรันบน VM เดียวกัน จึงวัดความสามารถของ CPU สำหรับงาน HTTP ไม่ใช่เครือข่าย
- อัตราเพิ่มเป็นขั้นตายตัว ค่าจึงถูกปัดเป็นขั้นและ CV มักเป็น 0% CV 0% ในข้อนี้ไม่ได้พิสูจน์ว่าเครื่องนิ่งสมบูรณ์
- ตัวยิงโหลดใช้ vCPU ร่วมกับ server จึงอาจใช้ CPU หมดก่อน run log เตือนให้ตรวจข้อนี้ใน log CPU ของ cpubench ที่บันทึกในโฟลเดอร์ผล ถ้าตัวยิงโหลดเป็นตัวจำกัด ค่านี้คือขอบล่างของ server

## sustain

โหลดทุกคอร์เป็นเวลานาน (ค่าเริ่มต้น 30 นาที) benchmark สั้น ๆ รันที่ความถี่ turbo แต่เครื่องที่ยุ่งหลายชั่วโมงจะรันที่ความถี่ที่ระบบระบายความร้อนและขีดจำกัดกำลังไฟยอมให้ stage นี้วัดความถี่นั้น รวมถึงกำลังไฟที่กินและความร้อนระหว่างทำ

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `sustain.stress-ng.all-core-mhz.max` | มาก | ความถี่เฉลี่ยของทุกคอร์ใน 5 นาทีสุดท้ายของโหลด หลังอุณหภูมินิ่งแล้ว คือความเร็วจริงที่ค่า CPU แบบ `max` ทุกตัวรันได้ภายใต้งาน batch ยาว ๆ เครื่องสองเครื่องที่ CPU รุ่นเดียวกันต่างกันได้ที่ค่านี้ เพราะการระบายความร้อน ขีดจำกัดกำลังไฟ หรือ profile ของ BIOS `sustain.txt` บอกว่าค่ามาจาก turbostat (แม่นยำ) หรือจากมุมมองของ kernel (VM อาจแสดงค่า nominal คงที่ ซึ่งไม่มีความหมาย) |
| `sustain.turbostat.pkg-temp.peak` | ค่าบริบท | อุณหภูมิสูงสุดของ CPU package ไม่ตัดสินด้วยตัวเอง: CPU ร้อนแต่รักษาความถี่ได้ถือว่าดี CPU เย็นแต่ throttle ไม่ดี |
| `sustain.turbostat.thermal-headroom` | มาก | Tjmax ลบค่าสูงสุดนั้น: เหลืออีกกี่องศาก่อน CPU ต้อง throttle ระยะเผื่อน้อยที่อากาศเข้า 24 °C แปลว่าวันที่ร้อนหรือพัดลมเสียหนึ่งตัวจะ throttle |
| `sustain.turbostat.pkg-watt.full` | น้อย | กำลังไฟของ CPU package (RAPL) ภายใต้โหลด น้อยกว่าที่ความถี่เท่ากันคือชิ้นส่วนที่ประหยัดกว่า |
| `sustain.ipmi.power.idle` | น้อย | กำลังไฟทั้งเซิร์ฟเวอร์จาก BMC ขณะว่าง เซิร์ฟเวอร์ว่างเป็นเรื่องปกติ ค่านี้จึงมีผลต่อค่าไฟมากกว่าที่คิด |
| `sustain.ipmi.power.load-50` | น้อย | กำลังไฟทั้งเซิร์ฟเวอร์ที่โหลด CPU 50% จุดทำงานปกติของเครื่องที่มีงานแต่ไม่เต็ม ใช้ตัวนี้คิด TCO |
| `sustain.ipmi.power.full` | น้อย | กำลังไฟทั้งเซิร์ฟเวอร์ภายใต้โหลดเต็ม: กำลังไฟและความเย็นของ rack ที่ต้องเตรียมไว้ |
| `sustain.ipmi.fan.peak` | ค่าบริบท | พัดลมที่หมุนเร็วที่สุดตอนจบโหลดเต็ม ใกล้ค่าสูงสุดของพัดลมแปลว่าไม่มีสำรองความเย็น |

ค่ากำลังไฟจาก BMC คือมิเตอร์ของเซิร์ฟเวอร์เอง ในการจัดซื้อมักตรวจทานกับ PDU ในนาทีเดียวกัน ถ้าไม่มี BMC (VM หรือไม่มี `ipmitool` แบบ root) ค่ากำลังไฟถูกข้าม บันทึกเฉพาะความถี่

## burnin

รันการทดสอบความทนทานระยะยาว (ค่าเริ่มต้น 48 ชั่วโมง) กับหน่วยความจำและดิสก์ เพื่อหาข้อบกพร่องของฮาร์ดแวร์หรือการตั้งค่า ไม่ได้วัดความเร็ว

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `burnin.errors` | น้อย (0) | จำนวนปัญหาที่พบ: stressapptest ไม่ผ่าน, fio ตรวจข้อมูลแล้วไม่ตรง, บรรทัด error ใหม่ใน kernel log และตัวนับ error ทุกตัวที่เพิ่มขึ้นระหว่างรัน (EDAC memory error, รายการใหม่ใน event log ของ BMC, media error และ error-log ของ NVMe ที่ทดสอบ) ค่าใดที่ไม่ใช่ 0 แปลว่ายังไม่ควรไว้ใจเครื่องนี้ให้เก็บข้อมูลจนกว่าจะหาสาเหตุเจอ |

รายละเอียดของแต่ละ error อยู่ใน `burnin.err`, `stressapptest.log`, `dmesg-errors.txt` และ `burnin-checks.txt` (ตัวนับก่อนและหลัง และตัวไหนเพิ่มขึ้น) ในโฟลเดอร์ผล เมื่อตั้ง `NVME_DEVS` การตรวจดิสก์รันบนทุกลูกที่ระบุพร้อมกัน

## info (ค่าบริบท)

ค่าเหล่านี้บันทึกไว้เพื่อให้ตีความค่าอื่นได้ แสดงในรายงานแต่ไม่ถูกตัดสิน

| ID | บอกอะไร |
|---|---|
| `info.cpu.steal.avg`, `info.cpu.steal.peak` | เปอร์เซ็นต์เวลาที่ VM ต้องการรันแต่ host ให้ CPU กับผู้อื่น ถ้า steal สูง ทุกผลในการรันนั้นต่ำกว่าที่เครื่องทำได้จริง และการเทียบกับการรันที่เงียบกว่าไม่ยุติธรรม รันใหม่ในช่วงที่เงียบกว่า หรือขอ CPU แบบ dedicated |
| `info.fio.fill-write-1m` | ความเร็วการเขียนไฟล์ทดสอบก่อนเริ่มทดสอบ disk ใช้ตรวจความสมเหตุสมผล ถ้าต่างจาก `disk.fio.seq-write-1m` มาก แปลว่า storage ทำงานต่างไปตอนสร้างไฟล์ (เช่น ระหว่างจองพื้นที่) |

## ควรดูค่าไหนสำหรับงานแบบใด

จุดเริ่มต้นสำหรับเลือกว่าจะดูอะไรก่อน ทุกงานยังขึ้นกับค่าที่ไม่ได้อยู่ในรายการด้วย

| งาน | ดูก่อน |
|---|---|
| Web หรือ API server | `web.cpubench.mix.max-rps`, ค่า `1t` ของ `cpu.cpubench.int.json`, `cpu.cpubench.int.regex` และ `cpu.cpubench.int.compress`, ค่า crypto ที่เกี่ยวกับ TLS และ latency ของเครือข่ายถ้า backend อยู่อีกเครื่อง |
| ฐานข้อมูล OLTP (PostgreSQL, MySQL) | ค่า `disk.wal.*`, `pg.pgbench.tpcb.tps` และ `pg.pgbench.tpcb.stability`, `disk.fio.randread-4k.qd1.p99`, ค่า `disk.fio.db-*`, `mem.lmbench.lat-mem-rd.1t` |
| Analytics และงาน batch | `mem.stream.triad.max`, ค่า `max` ของ cpu, `disk.fio.seq-read-1m` |
| Cache และที่เก็บข้อมูลในหน่วยความจำ | `mem.lmbench.lat-mem-rd.1t`, `cpu.cpubench.int.hashmap.*`, latency ของเครือข่าย |
| File, backup และ storage server | `disk.fio.seq-read-1m`, `disk.fio.seq-write-1m`, `net.iperf3.tcp.bidir`, `disk.wal.fdatasync.avg` ถ้า client รอให้การเขียนถาวร |
| เครื่องใดก็ตามที่จะเก็บข้อมูลสำคัญ | `burnin.errors` = 0 |
| เซิร์ฟเวอร์ bare metal ที่กำลังประเมิน | `sustain.stress-ng.all-core-mhz.max`, `sustain.ipmi.power.load-50`, ยอดรวม `nvme.*.all-disks` และ CV ของค่า `nvme.*.per-disk`, `pg.pgbench.tpcb.tps-per-watt`, `burnin.errors` = 0 และ `hardware.txt` (หรือ `hardware.json`) เทียบกับ data sheet ของผู้ขาย |

## Checklist สำหรับเครื่อง bare metal

vmbench เขียนขึ้นสำหรับ VM บนเครื่องจริงการรันเดียวกันยังบันทึกสิ่งที่ checklist ตรวจรับฮาร์ดแวร์ถาม และส่วนที่ไม่ใช่การวัดจะอยู่ในไฟล์แทน ID:

| รายการใน checklist | อยู่ที่ไหน |
|---|---|
| รุ่น CPU, stepping, microcode; เวอร์ชัน BIOS และ firmware ของ BMC; driver ความถี่, governor, turbo, C-state, SMT | `hardware.txt` (`lscpu`, `/sys/class/dmi/id`, `cpupower`, `dmidecode -t bios` และ `ipmitool mc info` แบบ root) |
| จำนวน DIMM ขนาดและความเร็วที่ตั้ง เสียบครบทุก channel | `hardware.txt` (`dmidecode -t memory` แบบ root ไม่ได้ก็ใช้มุมมอง EDAC) |
| รุ่น NIC, driver, firmware, offload | `hardware.txt` (`ethtool -i`, `ethtool -k`, `lspci`) |
| รุ่นและ firmware ของดิสก์ มีรุ่นละกี่ลูก | `hardware.txt`, `nvme-devices.txt` |
| ทุกข้อข้างบนในรูปฟิลด์ (สำหรับ spreadsheet หรือสคริปต์) | `hardware.json` (ดูด้านล่าง) |
| ความถี่ทุกคอร์ต่อเนื่อง, thermal headroom, กำลังไฟตอนว่าง / 50% / เต็ม, รอบพัดลม | ค่า `sustain.*` |
| ประสิทธิภาพต่อวัตต์ | `pg.pgbench.tpcb.tps-per-watt` |
| NVMe ทุกลูกพร้อมกัน และทีละลูก | ค่า `nvme.*` |
| Burn-in 48 ชั่วโมง พร้อมตัวนับ error ของหน่วยความจำ ดิสก์ BMC และ NVMe | `burnin.errors`, `burnin-checks.txt` |

### hardware.json

stage `info` เก็บ output ดิบของทุกคำสั่งด้านฮาร์ดแวร์ไว้ใน `hw/` (`lscpu.txt`, `dmidecode-memory.txt`, `net-<interface>.txt`, ...) แล้ว `hw.py` แปลงเป็น `hardware.json` ทุก key ข้างล่างมีเสมอ ค่าที่อ่านไม่ได้เป็น `null` (หรือ list ว่าง) และ `unavailable` บอกเหตุผล (`dmidecode -t memory: needs root or sudo -n`, `cpufreq: not exposed by the kernel (usual in a VM)`) ไม่มี serial number, asset tag, UUID, ชื่อเครื่อง, MAC และ IP

| Key | ฟิลด์ |
|---|---|
| `cpu` | `vendor`, `model`, `family`, `model_id`, `stepping` (ข้อความ: ARM เป็นแบบ `r3p1`), `microcode`, `sockets`, `cores_per_socket`, `threads_per_core`, `numa_nodes`, `mhz_min`, `mhz_max`, `cache` (`l1d`, `l1i`, `l2`, `l3` ตามที่ lscpu พิมพ์) |
| `freq` | `driver`, `governor`, `min_khz`, `max_khz`, `scaling_min_khz`, `scaling_max_khz`, `turbo` (`on` / `off`), `smt`, `cpuidle_driver`, `cpuidle_governor` |
| `system` | `sys_vendor`, `product_name`, `product_version`, `board_vendor`, `board_name`, `board_version`, `bios_vendor`, `bios_version`, `bios_date`, `bios_release`, `bmc` (`firmware`, `manufacturer`) |
| `memory` | `slots`, `populated`, `dimms` (`locator`, `size_mb`, `type`, `speed_mts`, `configured_mts`, `manufacturer`, `part`), `configured_speeds` (`{"4800": 16}`), `source` (`dmidecode` หรือ `edac`) |
| `nics` | หนึ่งรายการต่อ interface จริง: `name`, `state`, `speed_mbps`, `mtu`, `pci`, `model`, `driver`, `driver_version`, `firmware`, `offloads` (`{"tcp-segmentation-offload": "on"}` ไม่รวม feature ที่ fixed) |
| `disks` | `name`, `model`, `firmware`, `size`, `tran`, `rota` |
| `nvme`, `nvme_models` | `ctrl`, `model`, `firmware` ต่อ controller; จำนวน controller ของแต่ละรุ่น |
| `bmc` | `power_w`, `temperatures` (`{sensor: C}`), `fans` (`{sensor: RPM}`) ตอนเริ่มรัน |
| `unavailable` | สิ่งที่ไม่ได้บันทึก บรรทัดละเหตุผล |

**รุ่น CPU ของ ARM** บน arm64 `/proc/cpuinfo` ไม่มีชื่อรุ่น และ lscpu รู้จักเฉพาะ core ที่อยู่ในตารางของมัน ที่เหลือพิมพ์ `Model name: -` stage `info` จึงเก็บ `hw/cpu-id.txt` ด้วย: `CPU implementer`, `variant`, `part`, `revision` ของ cpu0 จาก `/proc/cpuinfo` และ `midr_el1` จาก `/sys` (บอกแค่แบบของ core ไม่มีข้อมูลระบุตัวเครื่อง) เมื่อ lscpu ไม่ให้ชื่อ `model` ของ `cpu` จะมาจาก id นี้: part ที่อยู่ในตารางได้ชื่อ (`Neoverse-N1`, `Neoverse-V2`, `Kunpeng-920`, `Ampere-1`, ...) part อื่นเขียนเป็น `HiSilicon part 0xd0f` บน ARM ที่มี id `family` คือ implementer (`0x48`) `model_id` คือ part (`0xd01`) และ `stepping` เป็น `r<variant>p<revision>` โฟลเดอร์ผลที่ไม่มี `cpu-id.txt` (vmbench 0.2.3 หรือเก่ากว่า) ไม่มีหมายเลข part: ฟิลด์ `model` จะเป็น `HiSilicon (model not reported, SVE2)` (vendor และ SVE2 หรือ SVE ถ้ามีใน flags) แทน `-` ส่วน x86 ใช้ค่าของ lscpu เสมอ

`hardware.txt` ยังเขียนเหมือนเดิม ไว้อ่านและ `diff` โฟลเดอร์ผลของรุ่นเก่าไม่มีทั้ง `hw/` และ `hardware.json`

**ฮาร์ดแวร์ที่ต่างกันใน `report compare`** เมื่อทุกโฟลเดอร์ที่เทียบมี `hardware.json` รายงานจะมีตาราง "ฮาร์ดแวร์ที่ต่างกัน" ต่อจากตารางสภาพแวดล้อม แสดงเฉพาะฟิลด์ที่ต่างกัน: แถวละฟิลด์ (microcode ของ CPU, `system.bios_version`, `memory.configured_speeds`, ...) และแถวละ DIMM, NIC, ดิสก์ หรือ NVMe controller ที่ต่างกัน จับคู่ด้วย locator, ชื่อ interface หรือชื่อ controller (ถ้ามีครบทุกรัน จะแสดงเฉพาะส่วนที่ต่าง เช่น `firmware=...`) ถ้าจำนวนรายการใน list ไม่เท่ากันจะมีแถวเช่น `จำนวน memory.dimms` ด้วย ใต้ตารางมีบรรทัดบอกว่าเทียบกี่ฟิลด์ ต่างกันกี่ฟิลด์ ถ้าไม่ต่างเลยจะมีแค่บรรทัดนั้น ค่าที่อ่านจาก `bmc` (กำลังไฟ อุณหภูมิ พัดลม ตอนเริ่มรัน) และ `unavailable` ไม่นำมาเทียบ เพราะเปลี่ยนทุกรันโดยที่ฮาร์ดแวร์ไม่ได้เปลี่ยน ถ้าโฟลเดอร์ใดไม่มี `hardware.json` (vmbench v0.1.0 หรือเก่ากว่า) จะไม่มีตาราง และคำเตือนจะบอกว่าโฟลเดอร์ใด ชีท Hardware ใน Excel ตัดสิน "Same?" จากฟิลด์ชุดเดียวกัน

ที่ยังไม่ครอบคลุม เพราะต้องใช้แอปจริง PDU หรือคนอยู่หน้าเครื่อง: การทดสอบธุรกรรมระดับแอป (Node.js, Go, PHP, Python), ค่าจาก PDU, การ export BIOS ผ่าน Redfish และการทดสอบ PSU failover
