# วิธีอ่านผลลัพธ์

[English](reading-results.md) · **ภาษาไทย**

คู่มือนี้อธิบายทุกค่าที่ vmbench บันทึก ว่าวัดอะไร ค่ามากหรือน้อยดีกว่า และมีผลกับการใช้งานเครื่องจริงอย่างไร หรือก็คือ ทำไมค่านี้ถึงควรวัด

คู่มือนี้ไม่ได้ให้เกณฑ์ผ่านหรือไม่ผ่าน เพราะตัวเลขเท่าไรถึง "พอ" ขึ้นกับงานของคุณ vmbench จึงออกแบบมาเพื่อ **เปรียบเทียบ** เครื่องกับเครื่อง (หรือเครื่องเดิมก่อนและหลังเปลี่ยนแปลง) ที่รันด้วยเวอร์ชันและการตั้งค่าเดียวกัน นิยามที่แน่นอนของแต่ละ ID (เครื่องมือ หน่วย ทิศทาง) อยู่ใน [tests.md](tests.md) ส่วนหน้านี้เน้นการตีความ

## วิธีอ่านรายงาน

แต่ละแถวของรายงานแสดง metric ID หนึ่งตัว พร้อมหน่วย ค่า จำนวนรอบ และ CV

| คอลัมน์หรือเครื่องหมาย | ความหมาย |
|---|---|
| Value | **ค่ากลาง (median)** ของทุกรอบ ค่ากลางไม่ถูกดึงด้วยรอบที่ช้าหรือเร็วผิดปกติเพียงรอบเดียว |
| Rounds | จำนวนครั้งที่รันการทดสอบนั้น ถ้ามีรอบเดียว จะไม่รู้ว่าผลแกว่งระหว่างรอบแค่ไหน |
| CV | สัมประสิทธิ์การแปรผัน คือส่วนเบี่ยงเบนมาตรฐานคิดเป็นเปอร์เซ็นต์ของค่าเฉลี่ย CV น้อยแปลว่าเครื่องให้ผลเหมือนเดิมทุกครั้ง |
| `*` | วัดครั้งเดียว ให้ถือเป็นข้อบ่งชี้ ไม่ใช่ข้อเท็จจริง |
| `!` | CV ตั้งแต่ 5% ขึ้นไป เครื่องไม่นิ่งระหว่างการทดสอบนี้ (VM อื่นแย่งทรัพยากร, ถูกลดความเร็ว, มีงานเบื้องหลัง) ให้หาสาเหตุก่อนนำไปเปรียบเทียบ |

ในการเปรียบเทียบ (`vmbench report compare A B`) โฟลเดอร์แรกเป็นฐาน และโฟลเดอร์อื่นทั้งหมดถูกตัดสินเทียบกับฐานนั้น:

- **better / worse (ดีกว่า / แย่กว่า)**: ความต่างมากกว่าความแกว่งของทั้งสองการรัน
- **not clearly different (ไม่ต่างกันชัดเจน)**: ความต่างอยู่ภายใน CV ที่มากกว่าของสองการรัน หรือภายใน 1% อย่ารายงานว่าฝั่งใดชนะ
- ค่าบริบท (ทิศทาง `none` เช่น CPU steal) แสดงให้เห็นแต่ไม่ถูกตัดสิน

อ่านคำเตือนที่ด้านบนของรายงานก่อนเสมอ เวอร์ชัน vmbench หรือ cpubench ที่ต่างกัน, `QUICK=1`, ขนาดการทดสอบหรือจำนวน vCPU ที่ต่างกัน, CPU steal สูง และ step ที่ล้ม แต่ละข้อทำให้การเปรียบเทียบไร้ความหมายได้

## หลักที่ใช้กับทุก stage

**Throughput กับ latency เป็นคนละคำถาม** throughput (IOPS, MB/s, TPS, RPS, Gbps) คือปริมาณงานที่เครื่องทำเสร็จต่อวินาทีเมื่อมีงานป้อนตลอด latency (us, ms, ns) คือเวลาที่งานชิ้นเดียวใช้ เครื่องหนึ่งอาจมี throughput สูงแต่ latency แย่ได้ในเวลาเดียวกัน และผู้ใช้มักรู้สึกจาก latency

**เปอร์เซ็นไทล์บอกเรื่องคำขอที่ช้า** p99 คือค่าที่ 99% ของการทำงานเร็วกว่า p99.9 คือค่าที่ 99.9% เร็วกว่า ถ้าหน้าเว็บหนึ่งหน้าต้องอ่านดิสก์ 50 ครั้ง การอ่านที่ช้า 1 ใน 100 ครั้งจะกระทบสัดส่วนใหญ่ของการเปิดหน้าเว็บ p99 และ p99.9 จึงมักสำคัญกว่าค่าเฉลี่ย

**`1t` กับ `max` ตอบคนละคำถาม** `1t` (หนึ่ง thread) บอกว่างานเดี่ยวทำได้เร็วแค่ไหน ซึ่งเป็นตัวจำกัดเวลาตอบสนองของงานที่แบ่งย่อยไม่ได้ เช่น query ฐานข้อมูลหนึ่งตัวหรือคำขอหนึ่งรายการ `max` (ทุก vCPU) บอกความสามารถรวมเมื่อมีงานหลายชิ้นพร้อมกัน อัตราส่วน `max / 1t` บอกว่าเครื่องกระจายงานไปยัง vCPU ได้ดีแค่ไหน ถ้าต่ำกว่าจำนวน vCPU มาก อาจเป็นเพราะใช้ core จริงร่วมกัน, ถูกจำกัดด้วยความร้อนหรือพลังงาน หรือแบนด์วิดท์หน่วยความจำไม่พอ

**มากดีกว่า ยกเว้นหน่วยที่เป็นเวลาหรือจำนวนเหตุการณ์ที่ไม่ดี** `ns`, `us`, `ms`, `count` และ packet loss น้อยดีกว่า ส่วนอื่นทั้งหมดมากดีกว่า รายงานใช้กฎนี้ให้แล้ว

**VM สะท้อน hypervisor พอ ๆ กับฮาร์ดแวร์** ผล disk รวม cache และการตั้งค่า storage ของ host ผล CPU ขึ้นกับรุ่น CPU ที่ hypervisor เปิดให้ guest เห็น และ VM อื่นบน host เดียวกันแย่งเวลาไปจาก VM ของคุณ (CPU steal) ความต่างมากระหว่างสอง VM อาจมาจากการตั้งค่า ไม่ใช่จากฮาร์ดแวร์

## cpu

วัดว่า vCPU รันโค้ดประเภทต่าง ๆ ได้เร็วแค่ไหน ความเร็ว CPU มีผลกับเกือบทุกอย่าง: การรับคำขอ, การบีบอัด, การเข้ารหัส, การรัน query, การ build

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `cpu.sysbench.prime.1t`, `cpu.sysbench.prime.max` | มาก | ลูปเลขจำนวนเต็มแบบง่าย ใช้เช็กเร็ว ๆ ระหว่างเครื่อง **สถาปัตยกรรมเดียวกัน** เท่านั้น คะแนนขึ้นกับ compiler และชุดคำสั่ง จึงห้ามใช้เทียบ x86 กับ ARM |
| `cpu.7z.rating.max` | มาก | benchmark ในตัวของ 7-Zip ที่บีบอัดและคลายการบีบอัด แทนงานเลขจำนวนเต็มทั่วไปที่มีการแตกแขนงและเข้าถึงหน่วยความจำ: การบีบอัด, ทำไฟล์ archive, งาน server หลายประเภท |
| `cpu.openssl.aes-256-gcm.1t`, `cpu.openssl.aes-256-gcm.max` | มาก | ความเร็วการเข้ารหัสด้วย AES ของฮาร์ดแวร์ สำคัญกับ TLS (HTTPS), VPN, ดิสก์เข้ารหัส และ backup เข้ารหัส ถ้าค่าต่ำมาก อาจแปลว่า guest มองไม่เห็นคำสั่ง AES ของ CPU (ตรวจชนิด CPU ที่ hypervisor เปิดให้) |

การทดสอบของ cpubench แบ่งงาน CPU เป็นหมวด แต่ละหมวดบันทึกทั้งแบบหนึ่ง thread และทุก vCPU ชื่อแต่ละตัวด้านล่างจึงแทน ID สองตัว เช่น `cpu.cpubench.int.json.1t` และ `cpu.cpubench.int.json.max` หน่วยมาจาก cpubench และต่างกันในแต่ละการทดสอบ แต่ภายในการทดสอบเดียวกัน ค่ามากดีกว่าเสมอ

| การทดสอบของ cpubench | แทนงานจริงแบบใด |
|---|---|
| `cpu.cpubench.int.compress.{1t,max}`, `cpu.cpubench.int.decompress.{1t,max}` | การบีบอัดใน web server (gzip), การจัดการ log, backup, layer ของ container image |
| `cpu.cpubench.int.hashmap.{1t,max}` | การค้นหาในตารางในหน่วยความจำ: cache, interpreter, application server ไวต่อ latency ของ cache และหน่วยความจำ |
| `cpu.cpubench.int.json.{1t,max}` | การแปลง JSON ไปและกลับ: เกือบทุก web API และ microservice |
| `cpu.cpubench.int.regex.{1t,max}` | การจับคู่รูปแบบข้อความ: แยก log, ตรวจข้อมูลนำเข้า, routing, ค้นหา |
| `cpu.cpubench.int.sort.{1t,max}` | การเรียงลำดับ: ฐานข้อมูล (ORDER BY, สร้าง index), ประมวลผลข้อมูล |
| `cpu.cpubench.float.fft.{1t,max}` | ประมวลผลสัญญาณ, งานเสียงและภาพ |
| `cpu.cpubench.float.matmul.{1t,max}` | คณิตศาสตร์เมทริกซ์: งานคำนวณเชิงตัวเลข, รันโมเดล machine learning แบบง่าย ได้ประโยชน์จากคำสั่งแบบ vector |
| `cpu.cpubench.float.nbody.{1t,max}` | การจำลองทางวิทยาศาสตร์ด้วยเลขทศนิยม |
| `cpu.cpubench.crypto.aes-gcm.{1t,max}` | เข้ารหัสข้อมูลปริมาณมาก (ข้อมูลใน TLS, เข้ารหัสดิสก์) |
| `cpu.cpubench.crypto.sha256.{1t,max}` | การทำ hash: checksum, ระบุเนื้อหาด้วย hash, ลายเซ็น, ตัดข้อมูลซ้ำ |
| `cpu.cpubench.crypto.ecdsa-p256.{1t,max}`, `cpu.cpubench.crypto.rsa2048-sign.{1t,max}` | งานกุญแจสาธารณะ: TLS handshake และการเซ็น token สำคัญกับ server ที่รับการเชื่อมต่อ HTTPS ใหม่จำนวนมาก |

วิธีอ่านกลุ่ม cpu:

- ดูหมวดที่ตรงกับงานของคุณ แทนการดูตัวเลขรวมตัวเดียว CPU สองตัวอาจชนะกันคนละหมวด
- บริการที่ต้องตอบเร็ว ให้ดูค่า `1t` เป็นหลัก งาน batch และผู้ใช้จำนวนมากพร้อมกัน ให้ดูค่า `max`
- CV สูงในกลุ่มนี้มักแปลว่ามี VM อื่นใช้ core จริงตัวเดียวกัน ให้ดู CPU steal ของการรันเดียวกัน

## mem

วัดว่า vCPU ย้ายข้อมูลเข้าออก RAM ได้เร็วแค่ไหน และการเข้าถึงหน่วยความจำหนึ่งครั้งใช้เวลาเท่าไร โปรแกรมที่ข้อมูลใหญ่เกิน cache ของ CPU (ฐานข้อมูล, cache, analytics, heap ของแอปขนาดใหญ่) มักถูกจำกัดด้วยหน่วยความจำมากกว่า CPU

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `mem.stream.triad.max` | มาก | แบนด์วิดท์หน่วยความจำเมื่อใช้ทุก vCPU ด้วยรูปแบบอ่าน-อ่าน-เขียน (`a = b + s * c`) เป็นตัวเลขตัวเดียวที่นิยมใช้ตอบว่า "เครื่องนี้ไหลข้อมูลผ่าน RAM ได้กี่ข้อมูลต่อวินาที" สำคัญกับการ scan, analytics, การบีบอัดข้อมูลก้อนใหญ่ และฐานข้อมูลในหน่วยความจำ |
| `mem.stream.copy.max` | มาก | แบนด์วิดท์หน่วยความจำสำหรับการคัดลอกล้วน ใกล้เคียงต้นทุนการย้าย buffer ไปมา (ชั้น network และ storage, การคัดลอกหน่วยความจำก้อนใหญ่) |
| `mem.lmbench.lat-mem-rd.1t` | น้อย | เวลาโหลดหน่วยความจำหนึ่งครั้งเมื่อข้อมูลไม่อยู่ใน cache ของ CPU (ชุดข้อมูลใหญ่ที่สุด, หนึ่ง process) สำคัญกับงานที่ไล่ตาม pointer: hash table, B-tree, โครงสร้างแบบลิงก์, interpreter latency ต่ำทำให้แต่ละขั้นเร็วขึ้น แม้ยังใช้แบนด์วิดท์ไม่เต็ม |

วิธีอ่านกลุ่ม mem:

- แบนด์วิดท์หารด้วยจำนวน vCPU ได้ส่วนแบ่งต่อ vCPU คร่าว ๆ ถ้าต่ำ การเพิ่ม vCPU จะไม่ช่วยให้งานที่หนักด้านหน่วยความจำเร็วขึ้นมากนัก
- latency ที่สูงกว่าเครื่องที่เทียบเคียงได้มาก อาจมาจากหน่วยความจำกระจายข้าม NUMA node หรือ host ขาดหน่วยความจำ
- เทียบแบนด์วิดท์เฉพาะการรันที่มีจำนวน vCPU เท่ากัน เพราะ STREAM ใช้ทุก vCPU

## disk

วัด storage ที่ VM เขียนลง พฤติกรรมของดิสก์กำหนดว่าฐานข้อมูล commit ได้เร็วแค่ไหน แอปเริ่มทำงานเร็วแค่ไหน และ backup กับ restore ใช้เวลานานเท่าไร ใน VM ตัวเลขเหล่านี้รวม cache ของ hypervisor และ storage backend จึงอาจสูงหรือต่ำกว่าดิสก์จริงมาก

การทดสอบแบบสุ่มและแบบเรียงลำดับใช้ direct I/O (ข้าม page cache ของ guest) บนไฟล์ทดสอบขนาด `FIO_SIZE` (ค่าเริ่มต้น 8 GB) หรือบน raw device เมื่อตั้ง `RAW_DEV` ส่วนการทดสอบ WAL ตั้งใจให้ต่างออกไป: เหมือน write-ahead log ของฐานข้อมูล คือเขียนลงไฟล์ใน `WAL_DIR` ตามปกติ แล้วเรียก `fdatasync` เพื่อบังคับให้ข้อมูลลงที่เก็บถาวร

**สุ่ม 4 KiB หลายคำขอพร้อมกัน** (ความสามารถเมื่อมีโหลดพร้อมกัน):

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `disk.fio.randread-4k.qd32x4` | มาก | อ่านแบบสุ่มโดยมีคำขอค้าง 128 รายการ คือความสามารถในการอ่านที่รองรับผู้ใช้จำนวนมากพร้อมกันหรือฐานข้อมูลที่งานยุ่ง |
| `disk.fio.randwrite-4k.qd32x4` | มาก | เขียนแบบสุ่มที่ความขนานเท่ากัน วัดหลังเขียนไฟล์จนเต็มแล้ว เพื่อให้ storage อยู่ในสภาวะคงที่ ไม่ใช่สภาพใหม่ที่เร็วกว่าปกติ |
| `disk.fio.mixed-70-30-4k.read`, `disk.fio.mixed-70-30-4k.write` | มาก | อ่าน 70% เขียน 30% ใกล้เคียงแอปจริงมากกว่าการอ่านหรือเขียนล้วน ให้อ่านสองค่าคู่กัน |

**อ่านแบบสุ่มทีละคำขอ** (สิ่งที่ผู้ใช้คนเดียวรอ):

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `disk.fio.randread-4k.qd1.p99` | น้อย | 99% ของการอ่านแต่ละครั้งเสร็จเร็วกว่าค่านี้ คำขอที่ต้องอ่านดิสก์หนึ่งครั้งโดยไม่มี cache จะรออย่างน้อยเท่านี้ในกรณีที่ช้า |
| `disk.fio.randread-4k.qd1.p999` | น้อย | 0.1% ของการอ่านที่ช้าที่สุด ค่าสูงในข้อนี้แสดงออกมาเป็นหน้าเว็บช้าเป็นครั้งคราวหรือ query หมดเวลา แม้ค่าเฉลี่ยดูดี |

**ไล่ระดับ queue depth** (storage รองรับความขนานได้แค่ไหน): `disk.fio.randread-4k.sweep-qd{1,4,16,32,64,128}` มากดีกว่า

- อ่านหกค่าเป็นเส้นกราฟ ไม่ใช่ทีละค่า IOPS ควรเพิ่มขึ้นตาม queue depth แล้วค่อย ๆ คงที่ จุดที่เริ่มคงที่คือความขนานที่ storage ใช้ประโยชน์ได้
- IOPS ที่ `qd1` ประมาณ `1 / latency` บอกความเร็วของคำขอทีละรายการต่อเนื่องกัน
- ถ้า IOPS หยุดเพิ่มตั้งแต่ queue depth น้อย ๆ การเพิ่ม worker ขนานจะไม่ได้ throughput ของดิสก์เพิ่ม มีแต่รอนานขึ้น

**เรียงลำดับ 1 MiB** (ย้ายข้อมูลก้อนใหญ่):

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `disk.fio.seq-read-1m` | มาก | อ่านไฟล์ขนาดใหญ่: restore, scan ตารางใหญ่, โหลดชุดข้อมูล, คัดลอก image |
| `disk.fio.seq-write-1m` | มาก | เขียนไฟล์ขนาดใหญ่: backup, นำเข้าข้อมูลจำนวนมาก, ส่ง log, build image |

**การทดสอบรูปแบบฐานข้อมูล** ใน `DB_DIR` (8 KiB คือขนาด page ของ PostgreSQL จึงตามรูปแบบ I/O ของมัน):

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `disk.fio.db-randread-8k` | มาก | อ่าน page แบบสุ่มที่ไม่อยู่ใน cache ของ PostgreSQL |
| `disk.fio.db-randwrite-8k` | มาก | เขียน page แบบสุ่ม เหมือนช่วง checkpoint และการเขียนเบื้องหลัง |
| `disk.fio.db-randrw-8k.read`, `disk.fio.db-randrw-8k.write` | มาก | รูปแบบ page ผสมคล้ายงาน OLTP |
| `disk.fio.db-seqwrite-1m` | มาก | เขียนเรียงลำดับก้อนใหญ่ เหมือนตอนโหลดข้อมูลจำนวนมากหรือสร้าง index |

**การทดสอบ WAL** (ความเร็วการ commit): แต่ละครั้งเขียน 8 KiB แล้วรอจน storage ยืนยันว่าข้อมูลลงที่เก็บถาวรแล้ว (`fdatasync`) ทำทีละครั้ง นี่คือสิ่งที่ฐานข้อมูลทำในทุก commit เมื่อตั้ง `synchronous_commit = on`

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `disk.wal.fdatasync.avg` | น้อย | เวลาเฉลี่ยที่ทำให้ commit หนึ่งครั้งถาวร client เดียวไม่สามารถ commit เร็วกว่านี้ได้ |
| `disk.wal.fdatasync.p99` | น้อย | commit ที่ช้า แสดงออกมาเป็น latency พุ่งเป็นช่วง ๆ ในแอปที่เขียนหนัก |
| `disk.wal.commit-iops.qd1` | มาก | จำนวน commit ที่ถาวรต่อวินาทีจากผู้เขียนคนเดียว คร่าว ๆ คือเพดานของธุรกรรมเขียนต่อวินาทีของการเชื่อมต่อเดียว |

สำหรับระบบที่ต้องไม่ทำข้อมูลที่ยืนยันการเขียนแล้วหาย (ฐานข้อมูล, คิว, file server) ค่า WAL เป็นตัวเลขที่สำคัญที่สุดกลุ่มหนึ่งที่ vmbench บันทึก ดิสก์อาจมี IOPS สูงแต่ยังช้าในข้อนี้ได้

วิธีอ่านกลุ่ม disk:

- ความต่างมากระหว่างสอง VM มักมาจากโหมด cache ของ hypervisor หรือ storage backend มากกว่าตัวดิสก์ การ cache การเขียนที่ host ทำให้ `fdatasync` ดูเร็ว แต่ข้อมูลอาจหายถ้า host ล่ม ถามว่าดิสก์ถูกตั้งค่าอย่างไรก่อนสรุป
- `disk.fio.randwrite-4k.steadystate` เป็นธง ไม่ใช่คะแนน 1 แปลว่า fio ตรวจพบว่าประสิทธิภาพการเขียนแบบสุ่มนิ่งแล้ว ถ้าเป็น 0 ค่า random write อาจยังเปลี่ยนแปลงอยู่
- ค่า disk วัดครั้งเดียวโดยค่าเริ่มต้น ใช้ `--disk-rounds N` ก่อนตัดสินใจจากความต่างเล็กน้อย

## pg

รัน benchmark ของ PostgreSQL เอง (pgbench, งานคล้าย TPC-B ที่เป็นธุรกรรมอ่านเขียนขนาดเล็ก) บน cluster ที่แยกไว้ รวม CPU, หน่วยความจำ และโดยเฉพาะ latency ของการ commit เข้าเป็นตัวเลขที่ใกล้เคียงแอป OLTP จริง

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `pg.pgbench.tpcb.tps` | มาก | ธุรกรรมต่อวินาทีเมื่อมี client 2 × vCPU คือความสามารถของเครื่องในฐานะ database server สำหรับงานที่เขียนหนัก |
| `pg.pgbench.tpcb.stability` | มาก | TPS นิ่งแค่ไหนตลอด 10 นาที 100 คือแบนราบสมบูรณ์ ค่าต่ำแปลว่ามีช่วงสะดุดเป็นระยะ มักมาจาก checkpoint หรือ storage หยุดชะงัก ซึ่งผู้ใช้รู้สึกเป็นช่วงที่ช้า |
| `pg.pgbench.latency.single` | น้อย | เวลาเฉลี่ยต่อธุรกรรมเมื่อมี client เดียว บอกต้นทุนของธุรกรรมหนึ่งรายการเมื่อทำลำพัง ส่วนใหญ่คือความเร็ว CPU บวก latency ของการ commit สำคัญกับแอปที่ทำงานกับฐานข้อมูลทีละขั้น |

วิธีอ่านกลุ่ม pg:

- TPS ถูกจำกัดด้วยทรัพยากรที่หมดก่อน มักเป็น latency ของการ commit (เทียบกับค่า WAL ในกลุ่ม disk) บางครั้งเป็น CPU
- ความนิ่งสำคัญพอ ๆ กับ TPS เครื่องที่ TPS ต่ำกว่าเล็กน้อยแต่นิ่งกว่า ให้บริการที่คาดเดาได้มากกว่า
- ผลขึ้นกับขนาดข้อมูล (`PG_SCALE`) และการตั้งค่า PostgreSQL เทียบเฉพาะการรันที่ scale และการตั้งค่าเหมือนกัน (`pg-settings.txt` ในโฟลเดอร์ผลบันทึกค่าเหล่านี้)

## net

วัดเส้นทางเครือข่ายระหว่าง VM นี้กับเครื่องปลายทาง สำคัญกับทุกอย่างที่คุยกับเครื่องอื่น: ฐานข้อมูลที่อยู่อีกเครื่อง, replication, storage ผ่านเครือข่าย, client

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `net.iperf3.tcp.tx`, `net.iperf3.tcp.rx` | มาก | throughput ของ TCP แต่ละทิศทางด้วย 8 stream การทดสอบส่งทั้งสองทาง **พร้อมกัน** สองค่านี้จึงแบ่งลิงก์กัน ไม่มีค่าไหนเป็นเพดานของทิศทางเดียว |
| `net.iperf3.tcp.bidir` | มาก | สองทิศทางรวมกัน เป็นค่าที่ใกล้ความสามารถรวมของเส้นทางที่สุดในสามค่านี้ สำคัญกับ backup, replication และการโอนข้อมูลก้อนใหญ่ |
| `net.sockperf.pingpong.avg` | น้อย | latency เฉลี่ยทางเดียวของข้อความขนาดเล็ก ทุกคำขอไปยังฐานข้อมูลหรือบริการบนเครื่องอื่นต้องจ่ายค่านี้อย่างน้อยสองครั้ง (ไปและกลับ) |
| `net.sockperf.pingpong.p99` | น้อย | ข้อความที่ช้า แสดงออกมาเป็นคำขอระหว่างบริการที่ช้าเป็นครั้งคราว |
| `net.iperf3.udp.pps` | มาก | จำนวน packet UDP ขนาดเล็ก (64 ไบต์) ที่ **ส่ง** ได้ต่อวินาที โดยส่งเร็วที่สุดเท่าที่ทำได้ บอกว่า network stack ของ VM ดัน packet เล็กได้กี่ packet: เกี่ยวกับ DNS, VoIP, เกม และ traffic อื่นที่ถูกจำกัดด้วยอัตรา packet |
| `net.iperf3.udp.loss` | น้อย | packet loss ที่อัตราการส่งแบบไม่จำกัดนั้น เนื่องจากไม่ได้จำกัดความเร็วฝั่งส่ง จึงคาดว่าจะมี loss บ้าง และไม่ได้แปลว่าเครือข่ายเสีย ใช้เทียบเครื่องที่ทดสอบแบบเดียวกัน |

วิธีอ่านกลุ่ม net:

- ผลบรรยาย **เส้นทาง** ไปยังเครื่องปลายทางที่เลือก รวมถึงตัวเครื่องปลายทางเอง เทียบเครื่องกับเครื่องเฉพาะเมื่อใช้ปลายทางเดียวกัน
- สำหรับแอปที่คุยถี่ (คำขอเล็ก ๆ จำนวนมาก) latency สำคัญกว่า throughput

## web

รัน HTTP server ขนาดเล็กและตัวยิงโหลดจาก cpubench บนเครื่องเดียวกัน (loopback) แล้วเพิ่มอัตราคำขอทีละขั้นจน latency ไม่ผ่านเป้าหมายของ cpubench

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `web.cpubench.mix.max-rps` | มาก | อัตราคำขอสูงสุดที่เครื่องรับได้ก่อน latency เริ่มพุ่งขึ้นชัน ("จุดหักเข่า" หรือ knee) เป็นตัววัดในทางปฏิบัติว่า CPU รับ traffic เว็บหรือ API ได้เท่าไรโดยยังตอบสนองดี |

วิธีอ่านกลุ่ม web:

- ทั้ง server และตัวยิงโหลดรันบน VM เดียวกัน จึงวัดความสามารถของ CPU สำหรับงาน HTTP ไม่ใช่เครือข่าย
- อัตราเพิ่มเป็นขั้นตายตัว ค่าจึงถูกปัดเป็นขั้นและ CV มักเป็น 0% CV 0% ในข้อนี้ไม่ได้พิสูจน์ว่าเครื่องนิ่งสมบูรณ์
- ตัวยิงโหลดใช้ vCPU ร่วมกับ server จึงอาจใช้ CPU หมดก่อน run log เตือนให้ตรวจข้อนี้ใน log CPU ของ cpubench ที่บันทึกในโฟลเดอร์ผล ถ้าตัวยิงโหลดเป็นตัวจำกัด ค่านี้คือขอบล่างของ server

## burnin

รันการทดสอบความทนทานระยะยาว (ค่าเริ่มต้น 48 ชั่วโมง) กับหน่วยความจำและดิสก์ เพื่อหาข้อบกพร่องของฮาร์ดแวร์หรือการตั้งค่า ไม่ได้วัดความเร็ว

| ID | ดีคือ | ความหมายในการใช้งานจริง |
|---|---|---|
| `burnin.errors` | น้อย (0) | จำนวนปัญหาที่พบ: stressapptest ไม่ผ่าน, fio ตรวจข้อมูลแล้วไม่ตรง, และบรรทัด error ใหม่ใน kernel log ค่าใดที่ไม่ใช่ 0 แปลว่ายังไม่ควรไว้ใจเครื่องนี้ให้เก็บข้อมูลจนกว่าจะหาสาเหตุเจอ |

รายละเอียดของแต่ละ error อยู่ใน `burnin.err`, `stressapptest.log` และ `dmesg-errors.txt` ในโฟลเดอร์ผล

## info (ค่าบริบท)

ค่าเหล่านี้บันทึกไว้เพื่อให้ตีความค่าอื่นได้ แสดงในรายงานแต่ไม่ถูกตัดสิน

| ID | บอกอะไร |
|---|---|
| `info.cpu.steal.avg`, `info.cpu.steal.peak` | เปอร์เซ็นต์เวลาที่ VM ต้องการรันแต่ host ให้ CPU กับผู้อื่น ถ้า steal สูง ทุกผลในการรันนั้นต่ำกว่าที่เครื่องทำได้จริง และการเทียบกับการรันที่เงียบกว่าไม่ยุติธรรม รันใหม่ในช่วงที่เงียบกว่า หรือขอ CPU แบบ dedicated |
| `info.fio.fill-write-1m` | ความเร็วการเขียนไฟล์ทดสอบก่อนเริ่มทดสอบ disk ใช้ตรวจความสมเหตุสมผล ถ้าต่างจาก `disk.fio.seq-write-1m` มาก แปลว่า storage ทำงานต่างไปตอนสร้างไฟล์ (เช่น ระหว่างจองพื้นที่) |

| งาน | ดูก่อน |

| เครื่องใดก็ตามที่จะเก็บข้อมูลสำคัญ | `burnin.errors` = 0 |
